# Функциональные требования: обработка файлов и медиа в Telegram-боте

## 1. Цель

Реализовать в Telegram-боте обработку файлов и медиа, отправленных пользователем.

Под файлами и медиа в рамках этих требований понимаются только три типа Telegram-вложений: документы (`document`), фотографии (`photo`) и видео (`video`). Остальные типы вложений бот должен игнорировать.

Бот должен:

1. принимать от авторизованного пользователя документы, фотографии и видео;
2. автоматически скачивать файлы размером до 20 МБ включительно;
3. не пытаться автоматически скачивать файлы размером больше 20 МБ через стандартный Telegram Bot API;
4. сохранять сведения о файлах больше 20 МБ в очередь ручного скачивания;
5. выдавать пользователю файлы из очереди, чтобы пользователь мог скачать их самостоятельно средствами Telegram;
6. выполнять базовую дедубликацию файлов;
7. удалять исходные сообщения пользователя после успешной обработки всех поддерживаемых файлов из сообщения;
8. игнорировать сообщения от всех пользователей, кроме заранее заданного авторизованного пользователя.

## 2. Ограничения Telegram Bot API

Стандартный метод `getFile` позволяет получить файл для скачивания только если размер файла не превышает 20 МБ.

Для файлов больше 20 МБ бот не должен выполнять автоматическое скачивание через `getFile`.

Для больших файлов бот должен хранить не содержимое файла, а только метаданные и идентификаторы Telegram, необходимые для последующей выдачи файла пользователю.

## 3. Термины

**Вложение** — поддерживаемый объект Telegram-сообщения, который содержит `file_id` и относится к одному из типов: `document`, `photo`, `video`.

**Файл** — обобщённое название поддерживаемого вложения. В рамках документа термин «файл» используется не только для Telegram-объекта `document`, но и для фото и видео.

**Малый файл** — файл или медиа размером до 20 МБ включительно.

**Большой файл** — файл или медиа размером больше 20 МБ.

**Очередь больших файлов** — общий список больших файлов и медиа от авторизованных пользователей, которые бот не скачал автоматически и должен показать пользователю пачками.

**Выдача файла пользователю** — отправка пользователю файла через Telegram по сохранённому `file_id`, чтобы пользователь скачал файл вручную.

**Дубликат файла** — файл или медиа, которые бот считает уже полученными ранее на основании выбранного набора признаков.

## 4. Общая логика обработки входящего сообщения

1. Пользователь отправляет боту сообщение с одним или несколькими поддерживаемыми вложениями: документами, фотографиями или видео.
2. Бот получает update от Telegram.
3. Бот определяет список поддерживаемых файловых и медиа-вложений в сообщении.
4. Бот обрабатывает вложения по одному.
5. Для каждого файла бот определяет:
   - тип вложения;
   - имя файла, если доступно;
   - размер файла, если доступен;
   - `file_id`;
   - `file_unique_id`;
   - `message_id`;
   - `chat_id`;
   - `user_id`.
6. Для каждого файла бот выполняет проверку на дубликат.
7. Если файл является дубликатом, бот не скачивает его повторно и не добавляет повторную запись в очередь больших файлов.
8. Если файл не является дубликатом, бот обрабатывает его по сценарию малого или большого файла.
9. После завершения обработки всех поддерживаемых файлов из сообщения бот удаляет исходное сообщение пользователя.
10. Бот отправляет пользователю итоговое сообщение о результате обработки.

## 5. Обработка малого файла или медиа

1. Пользователь отправляет файл или медиа размером до 20 МБ включительно.
2. Бот проверяет файл на дубликат.
3. Если файл не является дубликатом, бот вызывает `getFile`.
4. Бот скачивает файл по полученному `file_path`.
5. Бот сохраняет файл во внутреннее хранилище или передаёт его в дальнейшую обработку.
6. Бот фиксирует статус файла: `downloaded`.
7. Если файл является дубликатом, бот не скачивает его повторно и фиксирует статус: `duplicate_skipped`.

## 6. Обработка большого файла или медиа

1. Пользователь отправляет файл или медиа размером больше 20 МБ.
2. Бот проверяет файл на дубликат.
3. Если файл не является дубликатом, бот не вызывает `getFile` для скачивания.
4. Бот сохраняет в хранилище запись о файле:
   - `user_id`;
   - `chat_id`;
   - `message_id`;
   - `file_id`;
   - `file_unique_id`;
   - `file_name`;
   - `mime_type`;
   - `file_size`;
   - `file_kind`;
   - `received_at`;
   - `queue_position`;
   - `status = pending_manual_download`.
5. Бот добавляет файл в общую очередь больших файлов.
6. Если файл является дубликатом, бот не создаёт повторную запись в очереди и фиксирует статус: `duplicate_skipped`.

## 7. Базовая дедубликация

Бот должен выполнять базовую дедубликацию файлов и медиа, чтобы одинаковые вложения не скачивались и не добавлялись в очередь повторно.

### 7.1. Основной ключ дедубликации

Основной вариант дедубликации — по полю `file_unique_id`.

`file_unique_id` следует использовать как основной идентификатор одинакового файла внутри Telegram, потому что он предназначен для устойчивой идентификации файла между разными ботами и временем.

### 7.2. Дополнительные признаки дедубликации

Основной признак дедубликации — `file_unique_id`.

Имя файла не должно использоваться как ключ дедубликации, потому что разные файлы могут иметь одинаковое имя.

Для диагностики и отображения бот может дополнительно хранить:

- `file_size`;
- `file_name`;
- `mime_type`;
- тип вложения (`document`, `photo`, `video`).

Базовый ключ дедубликации:

```text
file_unique_id
```

Так как бот использует общую очередь и общую дедубликацию для всех авторизованных пользователей, пользовательский идентификатор не требуется включать в ключ дедубликации.

### 7.3. Поведение при дубликате

Если пользователь отправил файл или медиа, которые уже были обработаны ранее:

1. бот не скачивает файл повторно;
2. бот не добавляет повторную запись в очередь больших файлов;
3. бот учитывает файл в итоговом сообщении как пропущенный дубликат;
4. исходное сообщение пользователя всё равно удаляется после обработки всех файлов.

## 8. Обработка нескольких вложений и нескольких сообщений подряд

Пользователь может отправить:

- одно сообщение с одним вложением;
- медиагруппу/альбом с несколькими фото или видео;
- несколько сообщений подряд;
- большую серию сообщений, суммарно до 100 и более вложений.

Бот должен корректно обрабатывать все эти сценарии.

Бот должен:

1. принимать только поддерживаемые типы вложений: `document`, `photo`, `video`;
2. игнорировать все остальные типы вложений;
3. обрабатывать каждое поддерживаемое вложение отдельно;
4. для каждого вложения отдельно определять размер, тип и дубликатность;
5. для каждого вложения отдельно применять сценарий малого файла, большого файла или дубликата;
6. сохранять порядок вложений в соответствии с порядком получения от Telegram;
7. добавлять большие файлы в очередь в том же порядке;
8. корректно обрабатывать серии сообщений без ограничения на одну медиагруппу.

Telegram может присылать альбом или пачку файлов как набор отдельных updates. Поэтому бот не должен опираться на предположение, что все вложения одной пользовательской отправки придут в одном update.

Бот обрабатывает файлы из каждого update сразу: сохраняет записи, скачивает малые файлы, добавляет большие файлы в очередь и удаляет исходное сообщение.

Если Telegram передал `media_group_id`, бот не ждёт остальные updates этой медиагруппы для пользовательского ответа. Он отправляет отдельное сообщение по каждому обработанному файлу сразу после обработки соответствующего update.

Общая очередь должна сохранять порядок поступления вложений. Для пользователя результат должен выглядеть как единая накопительная очередь.

## 9. Удаление исходного сообщения пользователя

После того как бот завершил обработку всех файлов из сообщения, бот должен удалить исходное сообщение пользователя из чата.

Удаление допускается только после того, как все файлы из сообщения:

- успешно скачаны;
- либо добавлены в очередь ручного скачивания;
- либо распознаны как дубликаты;
- либо обработаны с ошибкой и ошибка зафиксирована.

Бот не должен удалять сообщение до завершения обработки всех файлов, чтобы не потерять доступ к данным сообщения в случае ошибки.

Если удалить сообщение не удалось, бот должен:

1. зафиксировать ошибку в логах;
2. не считать это критической ошибкой обработки файла;
3. не повторять удаление бесконечно.

## 10. Выдача больших файлов и медиа

Бот должен выдавать большие вложения пользователю пачками, но с приоритетом по типам вложений.

Поддерживаемые для выдачи типы вложений:

- `photo`;
- `video`;
- `document`.

Остальные типы вложений не должны скачиваться, не должны добавляться в очередь ручного скачивания и не должны выдаваться пользователю.

### 10.1. Выдача в порядке очереди

При обычной выдаче бот должен использовать следующий порядок:

1. сначала большие фотографии и видео;
2. после того как очередь больших фотографий и видео закончилась — большие документы.

Пока в общей очереди есть хотя бы одно большое фото или видео со статусом `pending_manual_download`, обычная выдача не должна выдавать документы.

### 10.2. Выдача фото и видео

1. Пользователь нажимает кнопку «Показать следующие вложения».
2. Бот ищет первые 10 вложений со статусом `pending_manual_download` и типом `photo` или `video`.
3. Если такие вложения найдены, бот отправляет пользователю до 10 фото/видео за один раз.
4. После успешной выдачи каждого вложения бот считает его скачанным пользователем и меняет его статус на `download_confirmed`.
5. Если часть вложений не удалось выдать, бот фиксирует ошибку только для этих вложений и продолжает обработку остальных вложений из пачки.
6. Бот сообщает пользователю общий остаток файлов в очереди ручного скачивания.

### 10.3. Выдача документов

1. Если в общей очереди не осталось больших фото или видео, бот переходит к выдаче документов.
2. Пользователь нажимает кнопку «Показать следующие вложения».
3. Бот ищет первые 10 документов со статусом `pending_manual_download`.
4. Если документы найдены, бот отправляет пользователю до 10 документов за один раз.
5. После успешной выдачи каждого документа бот считает его скачанным пользователем и меняет его статус на `download_confirmed`.
6. Если часть документов не удалось выдать, бот фиксирует ошибку только для этих документов и продолжает обработку остальных документов из пачки.
7. Бот сообщает пользователю общий остаток файлов в очереди ручного скачивания.
8. Если подходящих документов больше нет, бот сообщает, что очередь пуста.

### 10.4. Способ отправки вложений

Для выдачи больших вложений бот должен использовать сохранённый `file_id`.

Бот не должен использовать `copyMessage` или `forwardMessage` как основной механизм выдачи вложений из очереди.

При выдаче вложений бот должен выбирать метод Telegram Bot API по типу вложения:

- для `photo` — отправка фото по `file_id`;
- для `video` — отправка видео по `file_id`;
- для `document` — отправка документа по `file_id`.

Такой способ считается основным, потому что он не зависит от исходного сообщения пользователя и удобнее для выдачи вложений пачками до 10 штук.

### 10.5. Ограничение размера пачки

Бот должен выдавать не больше 10 вложений за одно пользовательское действие.

Если в очереди осталось меньше 10 подходящих вложений, бот выдаёт все оставшиеся подходящие вложения.

### 10.6. Выдача по размеру

Помимо обычной выдачи по очереди бот должен поддерживать выдачу файлов по размеру:

1. пользователь может запросить 10 самых больших файлов;
2. пользователь может запросить 10 самых маленьких файлов;
3. режимы по размеру выбирают только файлы со статусом `pending_manual_download`;
4. режимы по размеру сортируют файлы по `file_size`;
5. файлы с неизвестным размером не участвуют в выдаче по размеру;
6. при одинаковом размере порядок должен быть стабильным: `queue_position`, затем `received_at`, затем `id`;
7. после успешной выдачи каждого файла бот меняет его статус на `download_confirmed`.

Режимы выдачи по размеру не применяют приоритет фото/видео перед документами. Они сортируют все подходящие pending-файлы с известным размером.

### 10.7. Учет скачивания

Успешно выданные пользователю файлы считаются скачанными.

После успешной отправки файла через сохранённый `file_id` бот должен:

1. перевести запись файла из статуса `pending_manual_download` в статус `download_confirmed`;
2. записать событие `download_confirmed` в audit log;
3. не показывать этот файл в следующих выдачах очереди.

Если в хранилище остались записи со статусом `shown_to_user` от предыдущей версии логики, при следующем пользовательском действии бот может перевести их в `download_confirmed` для совместимости.

Бот не должен удалять историю файлов из хранилища после выдачи. Записи остаются в финальном статусе `download_confirmed`.

## 11. Команды и пользовательские действия

### `/show_queue`

Показывает summary общей очереди ручного скачивания:

- количество файлов в активной очереди;
- суммарный известный объём файлов.

### `/queue`

Команда отправляется ответом на медиа, ранее присланное ботом из очереди или архива.

Если файл найден по сообщению, бот возвращает запись в очередь ручной выдачи: `pending_manual_download` для файлов с известным размером или `pending_size_unknown` для файлов без размера. Файл снова считается не скачанным.

### `/archive`

Команда отправляется ответом на медиа, ранее присланное ботом из очереди или архива.

Если файл найден по сообщению, бот переводит запись в статус `archived`. Такой файл больше не показывается в обычной очереди, но может быть снова выдан через `/show_archive`.

### `/show_archive`

Показывает summary архива:

- количество файлов в архиве;
- суммарный известный объём файлов.

Кнопки выдачи архива аналогичны кнопкам очереди: следующая пачка, 10 самых больших, 10 самых маленьких.

### `/clear_queue`

Очищает общую очередь больших файлов.

Команда должна требовать явного подтверждения перед очисткой очереди.

### Кнопка «Показать следующие вложения»

Выдаёт следующую пачку из очереди ручного скачивания.

### Кнопка «10 самых больших»

Выдаёт до 10 самых больших файлов очереди с известным размером.

### Кнопка «10 самых маленьких»

Выдаёт до 10 самых маленьких файлов очереди с известным размером.

## 12. Функциональные требования

FR-01. Бот должен принимать от пользователя только документы, фотографии и видео. Остальные типы вложений бот должен игнорировать.

FR-02. Бот должен обрабатывать сообщения только от заранее заданного авторизованного пользователя. Сообщения от остальных пользователей бот должен игнорировать.

FR-03. Бот должен определять размер файла на основании поля `file_size`, если оно присутствует в объекте вложения.

FR-04. Если `file_size` отсутствует, бот должен обработать файл по безопасному сценарию: не скачивать файл автоматически, а сохранить его в очередь ручной выдачи со статусом `pending_size_unknown`.

FR-05. Бот должен автоматически скачивать через `getFile` только файлы размером до 20 МБ включительно.

FR-06. Бот не должен вызывать автоматическое скачивание через `getFile` для файлов больше 20 МБ.

FR-07. Для каждого большого файла или медиа бот должен сохранять метаданные вложения и идентификаторы Telegram, необходимые для последующей выдачи пользователю.

FR-08. Бот должен вести единую очередь больших файлов для всех авторизованных пользователей.

FR-09. Порядок файлов в очереди должен соответствовать порядку получения файлов ботом.

FR-10. Бот должен позволять пользователю получить следующую пачку больших вложений из очереди по кнопке «Показать следующие вложения».

FR-11. Бот должен выдавать пользователю большие вложения пачками не более 10 штук за одно пользовательское действие.

FR-12. После успешной выдачи большого файла бот должен менять его статус на `download_confirmed`.

FR-13. Бот должен поддерживать выдачу до 10 самых больших файлов очереди с известным размером.

FR-14. Бот должен поддерживать выдачу до 10 самых маленьких файлов очереди с известным размером.

FR-15. Режимы выдачи по размеру должны исключать файлы с неизвестным размером.

FR-16. Бот должен показывать пользователю количество оставшихся больших файлов в очереди.

FR-17. Бот должен поддерживать команду `/show_queue`, которая показывает summary общей очереди: количество файлов и суммарный известный объём.

FR-17a. Бот должен поддерживать команду `/queue`, которая в ответ на отправленное ботом медиа возвращает связанный файл в очередь как не скачанный.

FR-18. Бот должен поддерживать команду `/clear_queue`, которая очищает общую очередь больших файлов после явного подтверждения.

FR-18a. Бот должен поддерживать команду `/archive`, которая в ответ на отправленное ботом медиа переводит связанный файл в статус `archived`.

FR-18b. Бот должен поддерживать команду `/show_archive`, которая показывает summary архива и позволяет выдавать архивные файлы теми же режимами, что очередь.

FR-19. Бот должен не удалять скачанные малые файлы до завершения их обработки.

FR-20. Бот должен логировать результат обработки каждого файла или медиа-вложения.

FR-21. Бот должен выполнять базовую дедубликацию файлов по ключу `file_unique_id`.

FR-22. Если файл является дубликатом, бот не должен скачивать его повторно.

FR-23. Если большой файл является дубликатом, бот не должен создавать повторную запись в очереди ручного скачивания.

FR-24. Бот должен обрабатывать серии сообщений и медиагруппы, включая сценарий, когда пользователь отправляет до 100 и более вложений подряд.

FR-25. Бот должен обрабатывать вложения из одного сообщения, медиагруппы или серии сообщений последовательно, по одному.

FR-26. Бот должен удалять исходное сообщение пользователя после завершения обработки всех поддерживаемых файлов из этого сообщения.

FR-27. Если удалить исходное сообщение пользователя не удалось, бот должен зафиксировать ошибку и продолжить работу.

FR-28. Скачанные малые файлы должны сохраняться в директорию локальной файловой системы, заданную в конфигурации приложения.

## 13. Статусы файла

Рекомендуемые статусы:

```text
received
downloaded
pending_manual_download
pending_size_unknown
duplicate_skipped
shown_to_user
download_confirmed
download_failed
send_failed
expired_or_unavailable
deleted_by_user
archived
```

`received` — бот получил файл.

`downloaded` — файл до 20 МБ успешно скачан ботом.

`pending_manual_download` — файл больше 20 МБ добавлен в очередь ручной выдачи.

`pending_size_unknown` — размер файла не определён, файл отправлен в безопасный сценарий ручной выдачи.

`duplicate_skipped` — файл распознан как дубликат и не был обработан повторно.

`shown_to_user` — устаревший промежуточный статус: бот показал файл пользователю, но запись ещё не была переведена в финальный статус. Новая логика не должна создавать этот статус при успешной выдаче.

`download_confirmed` — файл был успешно выдан пользователю и считается скачанным.

`download_failed` — ошибка при скачивании малого файла.

`send_failed` — ошибка при выдаче большого файла пользователю.

`expired_or_unavailable` — исходное сообщение или файл больше недоступны для копирования/пересылки.

`deleted_by_user` — пользователь очистил очередь.

`archived` — пользователь временно убрал файл из очереди/скачанных без потери записи. Архивные файлы не показываются в обычной очереди.

Если исходное сообщение пользователя не удалось удалить, основной статус файла не перезаписывается. Ошибка фиксируется в `error_code = delete_message_failed` и `error_message`.

Минимальная таблица/коллекция `telegram_user_files`:

```sql
id

chat_id
message_id
media_group_id
file_id
file_unique_id
file_name
mime_type
file_size
file_kind
deduplication_key

```

Минимальная таблица/коллекция `telegram_sent_files` для связи отправленных ботом сообщений с файлами:

```sql
id
file_record_id
chat_id
sent_message_id
source

```

`file_size` должен храниться как 64-битное число.

`file_kind` используется для хранения исходного типа Telegram-вложения: `document`, `photo` или `video`.

`media_group_id` используется, если Telegram передал несколько файлов или медиа как медиагруппу/альбом.

`deduplication_key` рекомендуется формировать как:

```text
${file_unique_id}
```

Минимальная таблица/коллекция `telegram_file_events` для audit log:

```sql
id
file_record_id
file_unique_id
file_kind
status
event_type
error_code
error_message
created_at
```

В `telegram_file_events` логируется результат обработки каждого файла или медиа-вложения, включая `downloaded`, `pending_manual_download`, `pending_size_unknown`, `duplicate_skipped`, `download_failed`, `send_failed`, `delete_message_failed`, `download_confirmed`, `archived`, `returned_to_queue` и `deleted_by_user`.

Минимальная таблица/коллекция `telegram_bot_meta` для простых счетчиков:

```sql
key
value
created_at
updated_at
```

Счетчик `duplicate_skipped_count` хранит количество отсеянных дубликатов, потому что для дубликатов не создается отдельная запись в `telegram_user_files`.

## 15. Ошибочные сценарии

### 15.1. Ошибка скачивания малого файла

Если файл до 20 МБ не удалось скачать, бот должен:

1. установить статус `download_failed`;
2. сохранить текст ошибки;
3. сообщить пользователю, что файл не удалось скачать.

### 15.2. Ошибка выдачи большого файла

Если большой файл не удалось выдать пользователю, бот должен:

1. установить статус `send_failed`;
2. сохранить текст ошибки;
3. не переходить автоматически к следующему файлу;
4. сообщить пользователю, что файл не удалось показать.

### 15.3. Очередь пуста

Если пользователь нажимает «Показать следующие вложения», а очередь пуста, бот должен ответить:

```text
В очереди нет файлов для ручного скачивания.
```

### 15.4. Ошибка удаления сообщения пользователя

Если бот не смог удалить исходное сообщение пользователя, бот должен:

1. записать ошибку в лог;
2. не менять успешный статус обработки файлов;
3. установить `error_code = delete_message_failed` и сохранить текст ошибки в `error_message` для записей файлов, созданных в этом update;
4. записать событие `delete_message_failed` в `telegram_file_events`.

## 16. Нефункциональные требования

NFR-01. Приложение должно быть реализовано на Node.js.

NFR-02. Приложение должно использовать официальный Telegram Bot API.

NFR-03. Все ключи, токены и чувствительные параметры должны храниться в `.env` файле.

NFR-04. Значения из `.env` не должны попадать в логи, пользовательские сообщения или сообщения об ошибках.

NFR-05. Для отладки приложение должно запускаться напрямую из локального окружения разработчика.

NFR-06. Продакшн-версия приложения должна распространяться как Docker-образ.

NFR-06.1. Продакшн-версия приложения должна работать в режиме long polling.

NFR-07. Метаданные больших файлов должны храниться в постоянном хранилище, а не только в оперативной памяти процесса.

NFR-08. Общая очередь не должна теряться при перезапуске бота.

NFR-08.1. Очередь больших файлов должна храниться бессрочно, пока пользователь явно не очистит её или пока конкретные записи не будут переведены в финальный статус согласно пользовательскому действию.

NFR-09. Операции скачивания малых файлов должны выполняться с таймаутом.

NFR-10. Бот должен выдавать большие вложения пачками не более 10 штук за одно пользовательское действие.

NFR-11. Бот должен логировать технические события обработки файлов без сохранения содержимого файлов в логах.

NFR-12. Бот должен корректно обрабатывать повторный запуск после сбоя и не должен повторно скачивать уже обработанные файлы при наличии записи в хранилище.

- формат локального хранилища метаданных;

.env.example
.gitignore

package.json
src/
tests/

В `AGENTS.md` нужно зафиксировать:

## 18. Критерии приёмки

AC-01. Если пользователь отправляет файл размером 10 МБ, бот скачивает файл автоматически и переводит его в статус `downloaded`.

AC-02. Если пользователь отправляет файл размером 25 МБ, бот не вызывает скачивание через `getFile`, а создаёт запись в очереди со статусом `pending_manual_download`.

AC-03. Если пользователь отправляет три больших файла, бот сохраняет их порядок получения.

AC-04. При первом нажатии «Показать следующие вложения» бот показывает первую пачку из очереди, но не больше 10 вложений.

AC-05. После успешной выдачи каждого файла из пачки его статус меняется на `download_confirmed`.

AC-06. Повторное нажатие «Показать следующие вложения» показывает следующую пачку только из файлов, которые ещё находятся в статусе `pending_manual_download`.

AC-07. После выдачи всех файлов бот сообщает, что очередь пуста.

AC-08. После перезапуска сервиса общая очередь больших файлов сохраняется.

AC-09. Команда `/show_queue` показывает актуальное количество файлов в общей очереди и суммарный известный объём.

AC-10. Команда `/clear_queue` очищает очередь только после явного подтверждения пользователя.

AC-11. Если пользователь отправляет один и тот же файл дважды, бот скачивает его только один раз.

AC-12. Если пользователь отправляет один и тот же большой файл дважды, бот создаёт только одну запись в очереди.

AC-13. Если пользователь отправляет серию сообщений или медиагруппу, суммарно содержащую до 100 и более поддерживаемых вложений, бот обрабатывает их по одному и формирует корректную накопительную очередь.

AC-14. После завершения обработки всех файлов из сообщения бот удаляет исходное сообщение пользователя.

AC-15. Если исходное сообщение пользователя удалить не удалось, обработка файлов считается завершённой, основной статус файла сохраняется, а ошибка фиксируется в `error_code/error_message` и audit log.

AC-16. При нажатии «10 самых больших» бот выдаёт до 10 файлов с известным размером в порядке убывания `file_size`.

AC-17. При нажатии «10 самых маленьких» бот выдаёт до 10 файлов с известным размером в порядке возрастания `file_size`.

## 19. Принятые решения

1. Бот предназначен для использования списком авторизованных пользователей. Сообщения от остальных пользователей игнорируются.
2. Дедубликация выполняется по содержательной идентичности файла в Telegram: `file_unique_id`. Имя файла не используется как критерий уникальности.
3. Историю дубликатов хранить не нужно.
4. Поддерживаемые типы вложений: `document`, `photo`, `video`. Остальные типы игнорируются.
5. Бот должен корректно обрабатывать не только одну медиагруппу, но и серию сообщений с большим количеством вложений.
6. Очередь больших файлов хранится бессрочно.
7. Очередь не очищается автоматически после выдачи. Успешно выданные файлы сразу считаются скачанными и переводятся в `download_confirmed`.
8. Скачанные малые файлы сохраняются в директорию локальной файловой системы, заданную в конфигурации приложения.
9. В продакшне бот работает в режиме long polling.
10. Пользователь может получать файлы как в обычном порядке очереди, так и по размеру: 10 самых больших или 10 самых маленьких.
